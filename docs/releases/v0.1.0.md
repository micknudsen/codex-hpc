# codex-hpc v0.1.0

Initial release of the Python client for interactive Codex sessions in a single
workspace on a Slurm cluster. This release is available for site qualification;
real-cluster acceptance is still outstanding in
[#16](https://github.com/micknudsen/codex-hpc/issues/16).

## Features

- `codex-hpc setup` prepares the matching helper and signed image on the login
  host, verifies cached or downloaded artifacts, and activates the installation
  atomically without requesting compute resources.
- `codex-hpc connect WORKSPACE` validates the workspace and installation, requests
  one Slurm allocation, and runs interactive Codex in Apptainer on its assigned
  Linux x86-64 node. CPU, memory, time, account and partition are configurable.
- The selected workspace remains writable at its resolved remote path. Sessions
  use a private temporary home; workspace edits and the selected shared login
  persist across sessions. Browser callback sign-in and explicit device-code
  sign-in are supported.
- Owned-job cleanup, printed recovery commands, concurrent credential updates
  and safe retirement of obsolete managed files support session and upgrade
  recovery.

## Installation

```sh
conda create -n codex-hpc --override-channels -c micknudsen -c conda-forge codex-hpc=0.1.0
conda activate codex-hpc
codex-hpc setup --host my-cluster
codex-hpc connect '~/projects/example' --host my-cluster
```

The package requires Python >=3.9 and supplies OpenSSH as a dependency. The login
host needs Python 3, curl and Apptainer with PEM verification support. The cluster
needs Slurm, compatible Apptainer execution on Linux x86-64 compute nodes,
SSH access through the login host, and shared paths available on the compute
nodes. Cold setup requires login-host access to GitHub Releases. The image pins
Codex 0.170.0.

## Validation and limitations

Automated coverage includes Linux and macOS with Python 3.9 and 3.14, image
selection and reuse, and seven command suites against a fresh Conda installation
with the actual signed image. These tests use controlled SSH, Slurm and login
peers. Actual site forwarding, scheduler resource enforcement, production sign-in,
shared-filesystem behavior and cleanup still require real-cluster qualification.

Only one workspace and one Linux x86-64 node/task per session are supported.
The MVP milestone remains open until the real-cluster acceptance criteria pass.
